# on7o capture firmware for the M5Stack StickS3

Hold the button, speak, release. The audio streams to the on7o server **while you are still talking**.

Nothing is interpreted, answered, or acted upon here. The device is an input, and that is all it is: no LLM, no speech synthesis, no decisions.

## Hardware

The [M5Stack StickS3](https://docs.m5stack.com/en/core/StickS3): ESP32-S3-PICO-1-N8R8 (8 MB flash, 8 MB PSRAM), 1.14" LCD, and an **ES8311** audio codec with a MEMS microphone. M5Unified configures the codec for us, so no pin wrangling is needed.

Two things about the StickS3 matter to this firmware:

- the codec **cannot record and play at the same time**, so `M5.Speaker.end()` has to run before `M5.Mic.begin()`;
- StickS3 support landed in **M5Unified 0.2.12**; older versions will not see the board.

## Setup

Edit `on7o-capture/config.h`, the only file you should need to touch:

```c
#define ON7O_WIFI_SSID     "your-network"
#define ON7O_WIFI_PASSWORD "your-password"
#define ON7O_HOST          "192.168.15.92"   // printed by the server on startup
```

### Arduino IDE

1. Install the **esp32** board package (Espressif).
2. Install the **M5Unified** library (≥ 0.2.12) via Library Manager.
3. Open `on7o-capture/on7o-capture.ino`.
4. Board: **ESP32S3 Dev Module**. Set *PSRAM* = `OPI PSRAM`, *Flash Size* = `8MB`, *Partition Scheme* = `8M with spiffs`, *USB CDC On Boot* = `Enabled`.

### PlatformIO

```bash
cd m5sitcks3
pio run -t upload
```

## How it works

```
button down  ->  open HTTP connection, send headers
                 |
                 v
   [ mic block ] -> [ HTTP chunk ] -> server   (repeats every 32 ms)
                 |
button up    ->  drain queued blocks, send terminating chunk, read status
```

The upload uses **chunked transfer encoding**, so the device never has to know how long the thought will be before it starts sending, which is the whole point of push-to-talk. Audio goes out as raw PCM; the server wraps it in a WAV container, keeping the firmware free of any container bookkeeping.

Capture is **gapless**. M5Unified queues up to two recordings, so `audio_input.cpp` rotates three buffers: the one queued two calls ago is guaranteed to be full by the time the next `record()` returns, and can be uploaded while the microphone keeps running. `drainBlock()` then flushes what is still in flight after the button is released. Without it, the tail of every sentence is lost.

### Feedback on screen

| Display | Meaning |
|---|---|
| `on7o` / `hold to speak` | Idle, Wi-Fi up |
| `on7o` / `no wi-fi` (orange) | Idle, no connection |
| `REC` + seconds | Capturing and uploading |
| `sent` (green) | Server accepted the thought |
| `too short` | Under 400 ms, treated as an accidental bump, discarded |
| `no server` / `lost link` / `http NNN` | Upload failed |

## Configuration reference

| Define | Default | Notes |
|---|---|---|
| `ON7O_SAMPLE_RATE` | `16000` | What speech-to-text expects; 32 kB/s on the wire |
| `ON7O_BLOCK_SAMPLES` | `512` | 32 ms of audio, 1 kB per HTTP chunk |
| `ON7O_BUTTON` | `M5.BtnA` | G11. Switch to `M5.BtnB` (G12) for the other one |
| `ON7O_MIN_CAPTURE_MS` | `400` | Below this, discard instead of uploading |
| `ON7O_MAX_CAPTURE_MS` | `300000` | Safety stop for a button held in a pocket |

## Flashing notes

Three things about this board cost real time the first time around:

**Arduino's auto-reset does not work.** The USB CDC is generated by the ESP32-S3 itself, so when esptool asserts DTR/RTS to request a reset, the port it is holding disappears, and the board leaves the bus instead of coming back as the ROM. Every attempt dies at `could not open port`, before a single byte is sent.

The fix is to enter download mode by hand: **unplug, hold the side button, plug in while still holding, release after ~3 s.** Then flash with `--before no-reset`.

**The port alternates.** The board comes back as `/dev/ttyACM0` or `/dev/ttyACM1` depending on the enumeration. Check before pointing esptool at it.

**`303a:1001` is ambiguous.** The factory UiFlow2 firmware enumerates as `303a:832b`, but both ROM download mode *and* this firmware appear as `303a:1001` (USB-serial-JTAG). You cannot tell download mode apart by USB id alone: a black screen and silent serial are the real signals.

Also note that the side button **double-click powers the device off**, which looks alarming: the screen goes black, the USB device vanishes from the bus entirely, and the LED turns green (charging). A single click brings it back.

### Reading the serial output

`Serial` is the native USB CDC. Reading it with `cat` produces nothing useful. Use something that asserts DTR:

```bash
python3 -c "
import serial,sys
p=serial.Serial('/dev/ttyACM1',115200,timeout=1); p.dtr=True
while True:
    d=p.read(256)
    if d: sys.stdout.write(d.decode('utf-8','replace')); sys.stdout.flush()"
```

## Status

Compiles clean against esp32 core 3.3.11 + M5Unified 0.2.19 (1.1 MB flash, 33%; 52 kB static RAM, 16%).

**Runs on real hardware.** A 3-second capture reached the server intact: the firmware reported `status=201 bytes=97280` and the server stored exactly 97280 bytes of PCM, as a valid 16 kHz mono WAV with speech clearly visible in the envelope.

That first run on hardware exposed two defects, both since fixed:

- **Clipping.** M5Unified defaults `magnification` to 16, which drove peaks to 32752 of a 32768 full scale. Clipped audio costs speech-to-text accuracy. Now 4, via `ON7O_MIC_MAGNIFICATION`.
- **A dead first second.** The ES8311 emits exact zeros for close to a second after `M5.Mic.begin()`. Starting the microphone per capture therefore swallowed the first word of every thought. It now starts once at boot and stays running.

Battery life has not been measured, and the always-on microphone will matter there.
